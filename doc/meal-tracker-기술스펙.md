# meal-tracker 기술 스펙

- **문서 상태:** 결정 사항
- **대상 플랫폼:** Android 전용
- **관련 문서:** [제품 요구사항 문서](meal-tracker-PRD.md), [디자인 프로토타입](meal-tracker-디자인-프로토타입.html)

## 1. 기술 방향

네이티브 Android 앱으로 구현한다. 단일 개발자가 관리하기 쉬운 단일 앱 모듈과 로컬 우선 구조로 시작하고, 초기 버전에서는 로그인·백엔드·기기 간 동기화를 구현하지 않는다. 사용자가 기록한 식단과 목표는 기기 안에 저장하며, 네트워크 연결 없이 기록과 조회가 가능해야 한다.

## 2. 확정 스택

| 영역 | 기술 | 적용 기준 |
|---|---|---|
| 언어 | Kotlin | Android 앱 구현 언어 |
| UI | Jetpack Compose + Material 3 | 네이티브 화면과 앱 테마 구현 |
| 화면 이동 | Navigation Compose | 홈·달력·설정 3개 최상위 화면 이동 |
| 앱 구조 | UI/Data 계층, 화면별 ViewModel, Repository | 단방향 UI 상태 흐름을 사용하고 ViewModel 상태는 `StateFlow`로 제공 |
| 비동기·반응형 데이터 | Kotlin Coroutines + Flow | 데이터 조회 및 UI 상태 전달 |
| 구조화된 로컬 데이터 | Room (SQLite 기반) | 식단 기록, 음식 템플릿, 프로필, 날짜별 목표 이력 저장 |
| 간단한 앱 설정 | Preferences DataStore | 온보딩 완료 등 작은 키-값 설정 저장. 식단 데이터나 목표 이력에는 사용하지 않음 |
| 카메라 | CameraX | 영양성분표를 실시간 프레임으로 가져오기 |
| 텍스트 인식 | ML Kit Text Recognition 한국어 모델 | 기기 내부에서 한글·숫자 텍스트 인식 |
| 의존성 주입 | 초기에는 수동 주입 | 모듈과 객체 수가 늘어 복잡도가 생길 때 DI 라이브러리 도입을 재검토 |

### 2.1 Android SDK 기준

- 최소 지원 버전은 **Android 8.0 (API 26)**으로 한다.
- `compileSdk`와 `targetSdk`는 구현 시점의 Android 및 Google Play 요구사항에 맞춰 갱신한다. 현재 프로젝트 뼈대의 API 37 설정은 유지한 채 추후 실제 빌드 구성을 정리한다.
- Gradle, Android Gradle Plugin, Kotlin, Compose 및 라이브러리의 구체 버전은 구현을 시작할 때 호환되는 안정 버전으로 Version Catalog에서 함께 관리한다.

## 3. 앱 구조와 데이터 흐름

```text
Compose 화면
  ↓ 사용자 동작 / 상태 표시
ViewModel (화면 상태: StateFlow)
  ↓ 명령·조회
Repository
  ↓
Room DAO ── Room Database (기기 내부 SQLite)
```

- 화면은 상태를 표시하고 사용자 동작을 ViewModel에 전달한다.
- ViewModel은 Repository를 통해 데이터를 읽고 쓴다. 화면에서 Room DAO를 직접 호출하지 않는다.
- Room의 `Flow` 조회 결과를 ViewModel UI 상태로 변환해 기록 저장·수정 후 화면에 반영한다.
- 초기에는 별도 domain/use-case 계층과 다중 Gradle 모듈을 만들지 않는다. 계산 로직이 여러 화면에서 중복되거나 복잡해지면 추가한다.
- 세 최상위 화면은 홈(기록), 달력, 설정이다. 음식 입력과 편집은 해당 화면에서 진입하는 화면 또는 모달로 제공한다.

## 4. 로컬 저장 기준

### 4.1 Room 데이터

- `MealEntry`: 날짜, 섭취 시각, 식사 태그, 음식명 스냅샷, 섭취량·단위, 단위당 영양값과 실제 섭취분 칼로리·단백질 스냅샷.
- `Food`: 재사용 음식 템플릿. 이름, 기록 단위, 단위당 칼로리·단백질을 저장하며 등록 시 섭취 수량은 두지 않는다.
- `Goal`: 적용 칼로리·단백질 목표와 적용 시작일을 기록해 목표 변경 이력을 보존한다.
- `Profile`: 목표 추천에 사용자가 제공한 신체 정보. 추천 기능을 사용하지 않으면 필수 입력으로 요구하지 않는다.
- 음식 템플릿 변경·삭제가 과거 식단 기록을 바꾸지 않도록 식단 기록의 이름과 영양 스냅샷을 보존한다.
- 달력 히트맵과 연속 기록 일수는 기록에서 계산하며 별도 원본 데이터로 저장하지 않는다.
- 달력 날짜 셀은 숫자와 배경색만 표시하고, 미달성 / 일부 달성 / 모두 달성 단계는 색 농도로 구분한다. 화면 아래 텍스트 범례와 접근성 설명으로 색의 의미를 제공한다. 칼로리는 섭취량이 현재 적용 목표 이하일 때, 단백질은 목표 이상일 때 달성으로 계산한다. 오늘은 최종 상태 대신 진행 중으로 표시한다.

### 4.2 DataStore 데이터

- 온보딩을 완료했는지 등 앱 동작을 위한 작은 설정만 저장한다.
- 하루 영양 목표, 음식 템플릿, 식단 기록처럼 관계·이력·조건 검색이 필요한 데이터는 Room에 둔다.

### 4.3 백업과 동기화

- 초기 버전은 로컬 단일 사용자이며 계정·서버·동기화 기능을 포함하지 않는다.
- 앱 데이터 백업 및 기기 간 복구는 별도 제품 결정 전까지 보장하지 않는다.

## 5. OCR 기능 스펙

### 5.1 제품 범위

- OCR은 음식 템플릿 등록 및 수정의 보조 기능이다. 템플릿이 없어도 가능한 바로 기록 흐름을 대체하거나 막지 않는다.
- 음식 포장지의 영양성분표에서 칼로리와 단백질 값을 읽어 템플릿 입력 후보로 제공한다.
- 음식 종류를 사진으로 판별하거나 사진만으로 칼로리를 추정하지 않는다.
- OCR은 P1로 분류한다. 바로 기록, 합계, 달력 등 핵심 흐름을 먼저 구현한 다음 작업하되 전체 MVP 범위에는 포함한다.

### 5.2 실시간 인식 흐름

1. 음식 등록/수정 화면에서 사용자가 성분표 OCR을 시작한다.
2. 앱이 카메라 권한을 요청하고 CameraX 미리보기를 연다.
3. 별도 촬영 버튼 없이 미리보기 프레임을 ML Kit에 전달해 텍스트를 계속 분석한다.
4. 인식 결과에서 칼로리·단백질 후보를 추출한다. 영양표의 기준량과 사용자가 정한 기록 단위는 서로 다를 수 있으므로 자동 환산하지 않는다.
5. 후보값이 여러 프레임에서 안정적으로 인식되면 결과를 고정해 확인 화면에 표시한다.
6. 사용자가 추출값, 기준량, 기록 단위당 값의 관계를 확인하고 수정한 뒤 저장한다. 사용자 확인 전 템플릿이나 식단 기록에 자동 저장하지 않는다.

### 5.3 구현·오류 처리 기준

- OCR은 온디바이스 처리로 구현하고, 영양성분표 이미지를 외부 서버로 전송하지 않는다.
- 한국어 모델을 앱에 포함해 첫 사용 때 모델 다운로드를 요구하지 않는 구성을 기본으로 한다. 앱 용량 증가를 감수한다.
- 카메라 프레임 분석 중에는 최신 프레임 위주로 처리하고 중복 분석을 제한해 UI 멈춤과 불필요한 작업을 줄인다.
- 안정 프레임 수와 인식 신뢰도 기준은 실제 기기에서 확인해 정한다.
- 카메라 권한 거부, 인식 실패, 값 누락, 흐린 화면, 불확실한 값은 안내하고 수동 입력으로 이어지게 한다.
- OCR 화면을 닫거나 취소하면 추출값은 저장하지 않는다.
- 갤러리 이미지 선택은 초기 범위에 포함하지 않는다. 필요성이 확인되면 후속 추가한다.

## 6. 보안·개인정보 기준

- 초기 데이터는 기기 로컬에만 둔다. OCR 이미지도 서버로 보내지 않는다.
- 카메라 권한은 OCR 진입 시점에 요청하고, 권한이 없어도 직접 기록과 음식 템플릿 수동 입력을 사용할 수 있게 한다.
- 신체 정보와 식단 기록을 광고·분석 목적의 외부 서비스로 전송하지 않는다.

## 7. 현재 프로젝트에서 필요한 전환

현재 저장소에는 Android 애플리케이션 뼈대가 있으며 `compileSdk`/`targetSdk`는 37, `minSdk`는 24다. Gradle 설정은 AppCompat/Views와 Java 11을 사용하고 실제 Kotlin/Compose 화면은 아직 없다.

구현을 시작할 때 다음 작업을 반영한다.

- Kotlin 및 Compose 플러그인과 Compose BOM/Material 3 의존성 구성
- `minSdk`를 26으로 조정하고 Kotlin/JVM 및 Android Gradle Plugin 호환 설정 정리
- Navigation Compose, Lifecycle ViewModel/Compose 연동, Coroutines/Flow 의존성 구성
- Room과 KSP 구성 및 데이터베이스 마이그레이션 정책 마련
- Preferences DataStore 구성
- OCR 단계에서 CameraX와 한국어 ML Kit 텍스트 인식 의존성 추가

## 8. 후속 결정

- Room 스키마와 버전별 마이그레이션 정책
- OCR의 영양표 영역·숫자 추출 파서와 프레임 안정화 기준
- 사용자 목표 변경 시 과거 달력 달성률을 과거 목표 또는 현재 목표 중 무엇으로 계산할지
- 로컬 백업/내보내기 지원 시점과 방식
